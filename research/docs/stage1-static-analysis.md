# Stage 1: static analysis of NCBI tools

## Review outcome

**Review outcome: go for the bounded standalone feasibility build.** The most important discoveries are that the current `igblastn` executable unconditionally starts a worker and a formatter thread even with one search worker, and that its build explicitly requires VDB/SRA support even for a FASTA-only use case. The toolkit also declares LMDB and SQLite as build requirements for `seqdb`; selecting database version 4 is not by itself a way to remove those requirements. The user authorized Stage 2 with FASTA-only scope and explicitly excluded porting VDB; SRA access is not required. The later implementation findings and final feasibility outcome are summarized in [Stage 7](stage7-final-report.md).

The user must decide whether to proceed to Stage 2. No compilation, execution or source modifications were performed as part of this review.

## What VDB, LMDB and SQLite are

- **VDB (NCBI Virtual Database)** is NCBI's library for accessing data including reads in the Sequence Read Archive (SRA). IgBLAST supports SRA accessions as an alternative to FASTA input; the current `igblastn` target declares VDB as a build requirement even when only FASTA is used. A FASTA-only build might avoid it, but that would require investigating and potentially changing the build and SRA-related code. [NCBI VDB source](https://github.com/ncbi/ncbi-vdb).
- **LMDB (Lightning Memory-Mapped Database)** is an embedded key-value database library that uses memory-mapped files. NCBI's BLAST database format 5 uses LMDB for indexes. Database format 4 can avoid the v5 LMDB runtime path, but the reviewed toolkit's build still declares LMDB as a dependency; disabling it is not established by selecting v4. [LMDB source](https://github.com/LMDB/lmdb), including [liblmdb](https://github.com/LMDB/lmdb/tree/mdb.master/libraries/liblmdb).
- **SQLite3** is the version 3 API/library of SQLite, an embedded, serverless SQL database engine; it does not require a separate database server. One confirmed NCBI use is taxonomy filtering: BLAST can read `taxonomy4blast.sqlite3` and query descendants of a supplied taxonomic ID. The [taxonomy implementation](https://github.com/ncbi/ncbi-cxx-toolkit-public/blob/f83dd16a0c30899da66d4f6902b5a9ed36c9d433/src/objtools/blast/seqdb_reader/tax4blastsqlite.cpp#L38-L67) opens that database read-only and contains the recursive query; [argument processing](https://github.com/ncbi/ncbi-cxx-toolkit-public/blob/f83dd16a0c30899da66d4f6902b5a9ed36c9d433/src/algo/blast/blastinput/blast_args.cpp#L2393-L2444) invokes it for descendant taxonomic filtering. This is a confirmed use, not a complete inventory of all SQLite uses. Whether the specified FASTA/custom-germline workflow opens a SQLite database at runtime has not been established, but `seqdb`, `blastinput`, and `blast_app_util` declare SQLite as a **build** requirement regardless. [SQLite source repository](https://sqlite.org/src/dir?ci=trunk) and [SQLite overview](https://www.sqlite.org/about.html).

These are separate libraries serving different purposes: VDB accesses archive data, LMDB supports BLAST database indexing, and SQLite supports SQL-backed features including taxonomy lookups. The presence of a build dependency does not itself prove that the corresponding feature or data file is used at runtime. Browser compatibility remains to be tested.

Emscripten's [pthreads documentation](https://emscripten.org/docs/porting/pthreads.html) requires `-pthread` at compile and link, and browser cross-origin isolation for `SharedArrayBuffer`; it also warns that threaded and non-threaded builds are separate variants. Its [filesystem documentation](https://emscripten.org/docs/api_reference/Filesystem-API.html) confirms MEMFS is in-memory by default and browser VFS behavior differs from native disk. Cross-origin isolation can affect the later OGRDB fetch and package assets; this Stage does not test CORS.

## Stage 2 proposal if authorized

1. Select and pin the Emscripten SDK, CMake/generator, Windows build tools and cross-compiled third-party dependencies. Keep NCBI at the reviewed commit unless a different release is explicitly chosen; record changes. If a Python/Conda environment or additional Python tools are needed, ask the user which Conda environment to use.
2. Obtain or prepare a tiny, legitimately usable human IGH V/D/J, `.aux`/`.ndm` and query fixture. Establish a native comparator built from the same commit, recording exact settings and tool version output.
3. Configure the smallest complete FASTA-only target closure and remove VDB/SRA dependencies through documented, narrowly scoped build and source changes. Do not port VDB. Verify whether other linked libraries depend on it; if removal requires a larger change, stop and report the blocker. Diagnose LMDB, SQLite and platform features separately.
4. Build `makeblastdb`, then `igblastn` using compatible Emscripten settings. Begin the IgBLAST test as a pthread build rather than assuming `-num_threads 1` is thread-free. Serve localhost with required isolation headers and test a worker/pool setup.
5. In a minimal standalone browser harness, run v4 `makeblastdb` on all three references and explicitly transfer output files to the IgBLAST module. Run real `igblastn` with custom data and AIRR format 19. Compare row counts, query IDs and representative annotations against native; capture missing-file and malformed-input failures.
6. Preserve patches, build flags, commands, exact dependency licenses, logs and failures; stop at the second review gate. A failed build, workaround requiring a major rewrite, partial success or Node-only/native-only result is not browser feasibility.

**Stage 1 decision:** the user authorized proceeding to Stage 2 as a FASTA-only standalone build; SRA and VDB porting are out of scope. The static evidence did not promise a clean port or acceptable large-file performance. The Stage 2 build and runtime evidence is documented separately.
